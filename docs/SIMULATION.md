# Simulation semantics, v0.1

## Reproducibility

The engine uses an integer millisecond virtual clock. Events are ordered by scheduled time and then by their monotonically increasing scheduling sequence. The clock advances directly to the next event; the engine does not sleep in real time. Random link jitter uses the scenario's seeded generator. Identical model inputs, seed, and engine version yield identical metrics, verdicts, and traces.

Run IDs and creation timestamps intentionally differ. The stored SHA-256 model hash identifies the full serialized project snapshot, including names and graphical positions; it does not claim behavioural equivalence between different layouts.

## Request lifecycle

Each logical request receives a stable request ID. Retries share that ID but have a new attempt number. Requests arrive according to requestCount and intervalMs. Each attempt has its own timeout. It traverses the specified service pipeline and may wait for a free processing slot at each stage.

The database optionally deduplicates by logical request ID. With deduplication disabled, each delivered attempt can produce another write. Duplicate writes count writes beyond the first write for a logical request. With deduplication enabled, repeated attempts are processed but do not create additional writes.

If dropFirstResponse is enabled, the first successful response generated by the database for every logical request is lost before entering the return path. The operation has already been processed by the database. Subsequent responses can arrive normally. Link jitter is sampled independently for each traversal.

Timed-out work is not implicitly cancelled. An earlier attempt may still produce a write or response while a retry is in flight. Once the client has exhausted retries and timed out, it ignores later responses; server work still drains so duplicate-write metrics reflect those effects. Once a request completes, no further retries are scheduled for it.

For simultaneous events, scheduling sequence decides ordering. A timeout scheduled earlier than a response at the exact same timestamp executes first. This explicit boundary convention is covered by tests.

## Metrics and requirements

- Completed means that the client received an accepted response.
- Failed means a logical request exhausted its client retry policy without an accepted response.
- Attempts counts original sends and retries.
- Writes counts committed operations, including duplicates if protection is disabled.
- Latency is first send to first accepted response for a completed request.
- p95 uses the nearest-rank percentile of completed-request latencies.
- Duration includes draining in-flight server work; it may exceed the last client completion.
- The p95 requirement also fails if not all requests complete, preventing dropped work from producing a misleading latency pass.

The engine evaluates assertions over this defined model. Test verdicts are not proofs of all possible executions, and performance results depend on the chosen workload and processing/link assumptions.

## Replay

Simulation runs on the Go backend and returns a recorded trace. Browser Play, Pause, Step, and Reset navigate that trace. Replay speed changes presentation speed only; it does not modify the simulation or its results.

## Validation and bounds

Validation checks schema version, finite bounded fields, unique IDs, references, component roles, and the supported linear topology. The engine also enforces execution time/event bounds and checks context cancellation. Failed or cancelled executions are reported as errors rather than persisted as successful partial results.
