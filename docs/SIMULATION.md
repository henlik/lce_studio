# Simulation semantics, v0.3

The engine supports three explicitly selected project schemas. Schema 1 retains the original application-only pipeline semantics described first. Schema 2 adds the infrastructure-coupled execution described below. Schema 3 adds exclusive branching, convergence and reusable declarative component profiles, with optional infrastructure. None of these schemas executes imported application code. Engine version 0.3.0 records which implementation produced a run; persisted older runs retain their original version and snapshots. Schema-1 and schema-2 execution semantics are unchanged.

## Reproducibility

The engine uses an integer millisecond virtual clock. Events are ordered by scheduled time and then by their monotonically increasing scheduling sequence. The clock advances directly to the next event; the engine does not sleep in real time. Random link jitter uses the scenario's seeded generator. Identical model inputs, seed, and engine version yield identical metrics, verdicts, and traces.

Run IDs and creation timestamps intentionally differ. The stored SHA-256 model hash identifies the full serialized project snapshot, including names and graphical positions; it does not claim behavioural equivalence between different layouts.

## Request lifecycle

Each logical request receives a stable request ID. Retries share that ID but have a new attempt number. Requests arrive according to requestCount and intervalMs. Each attempt has its own timeout. It traverses the specified service pipeline and may wait for a free processing slot at each stage.

The database optionally deduplicates by logical request ID. With deduplication disabled, each delivered attempt can produce another write. Duplicate writes count writes beyond the first write for a logical request. With deduplication enabled, repeated attempts are processed but do not create additional writes.

If dropFirstResponse is enabled, the first successful response generated by the database for every logical request is lost before entering the return path. The operation has already been processed by the database. Subsequent responses can arrive normally. Link jitter is sampled independently for each traversal.

Timed-out work is not implicitly cancelled. An earlier attempt may still produce a write or response while a retry is in flight. Once the client has exhausted retries and timed out, it ignores later responses; server work still drains so duplicate-write metrics reflect those effects. Once a request completes, no further retries are scheduled for it.

For simultaneous events, scheduling sequence decides ordering. A timeout scheduled earlier than a response at the exact same timestamp executes first. This explicit boundary convention is covered by tests.

## Metrics and requirements

- Completed means that the client received an accepted response.
- Failed means a logical request exhausted its client retry policy without an accepted response.
- Attempts counts original sends and retries.
- Writes counts committed operations, including duplicates if protection is disabled.
- Latency is first send to first accepted response for a completed request.
- p95 uses the nearest-rank percentile of completed-request latencies.
- Duration includes draining in-flight server work; it may exceed the last client completion.
- The p95 requirement also fails if not all requests complete, preventing dropped work from producing a misleading latency pass.

The engine evaluates assertions over this defined model. Test verdicts are not proofs of all possible executions, and performance results depend on the chosen workload and processing/link assumptions.

## Replay

Simulation runs on the Go backend and returns a recorded trace. Browser Play, Pause, Step, and Reset navigate that trace. Replay speed changes presentation speed only; it does not modify the simulation or its results.

## Validation and bounds

Validation checks schema version, finite bounded fields, unique IDs, references, component roles, package locks, and the topology supported by the selected schema. The engine also enforces execution time/event bounds and checks context cancellation. Failed or cancelled executions are reported as errors rather than persisted as successful partial results.

## Schema 2: placement and shared resources

The application remains a single client → service(s) → database pipeline. Every application node has one host placement. Hosts belong to geographical sites and declare CPU cores, resident memory capacity, idle/active CPU power, and power-outage windows. The tier and geographic coordinates are annotations: they do not invent processor speed, propagation delay, mobility, or connectivity. All cross-host communication requires one explicitly defined direct physical link; multihop routing is not supported in this increment.

Each service or database job occupies one CPU core for its configured processingMs. A node's capacity still limits the number of jobs that node can process simultaneously. Colocated nodes compete for the same host CPU cores. Work enters a host queue in arrival order; the scheduler selects the earliest waiting job whose node has an available slot. It repeats while a host core is free. This is work-conserving FIFO admission among eligible jobs; a node at capacity does not block unrelated eligible work.

Each application node reserves its configured memoryMb, including the client. Omitted or zero memoryMb means 64 MiB. The validator rejects deployments whose summed reservations exceed host memory. There is no dynamic allocation, swapping, memory-bandwidth contention, operating-system overhead, CPU clock-speed model, or OOM simulator. Response forwarding and client orchestration consume no CPU slots in the current abstraction.

## Schema 2: physical transfers

A request or response crossing a physical link carries exactly infrastructure.messageBytes. Both directions share one FIFO transmission channel; its serialization time in integer milliseconds is:

```text
ceil(messageBytes × 8 / bandwidthKbps)
```

The channel becomes free after serialization. Propagation then adds the physical link latency, the corresponding application edge latency, and one seeded uniform jitter sample. Thus another message may start transmission while a previous one is still propagating. Application edges on the same host use only their application latency and jitter, without a physical transfer or serialization cost. The jitter sample is drawn when propagation begins; stable event ordering makes this deterministic.

Every attempted crossing increments the physical link's transfers count, including an attempt immediately rejected because its link or an endpoint is down. bytesTransferred counts only complete payloads delivered successfully. droppedTransfers counts failed attempts, including messages waiting in the channel queue. Partial byte delivery, packet retransmission, protocol overhead, TCP behaviour, wireless interference, and link energy are not modelled. On a completed run, each link obeys:

```text
bytesTransferred = (transfers − droppedTransfers) × messageBytes
```

## Schema 2: outages, boundaries and recovery

Outage intervals are half-open [startMs, endMs). Environmental transitions execute before application or transport events at the same timestamp. A host or link is available at the end of its outage and unavailable at the start. Touching outage windows form one continuous unavailable period even if their input ordering differs.

Host power loss immediately discards both active and queued volatile processing on that host. interruptedJobs counts both categories. Cores and node slots are released; cancelled completion events do not later write data. Already committed database writes and request-ID deduplication state persist through a power cycle. The durability assumption covers a process/power cycle of intact persistent storage, not disk destruction or site loss.

Host or link outages also drop queued and in-flight transfers, including messages in their propagation delay. The current conservative transfer model requires both endpoints and the physical link to remain available throughout a transfer's lifetime; it does not model packets already buffered elsewhere surviving an endpoint power cycle. Same-host delayed messages are also volatile and are discarded by host power loss.

Power/network restoration makes new work eligible. It does not automatically replay interrupted jobs or dropped messages. The existing bounded client retry policy is responsible for new attempts, with their original logical request IDs. Timed-out server work continues unless an infrastructure failure interrupts it. A committed write can therefore exist even if the client ultimately reports failure; replay makes that distinction visible.

The workload generator is external to the simulated client host and retains schedules, retry budgets and timers. An unavailable client host prevents its send/receive, but already scheduled timeouts still expire and can trigger retries. This is an explicit experiment abstraction, not a claim that an unpowered client device can execute timers. Zero boot and service-recovery delay is assumed at the end of an outage; boot delays, batteries and migration are future capabilities.

## Schema 2: energy and observation horizon

While powered, a host draws the following CPU-related power:

```text
idleWatts + (activeWatts − idleWatts) × busyCores / cpuCores
```

A down host draws zero. Between successive effective events the engine integrates this constant load, converting W·ms to Wh by dividing by 3,600,000. busyCoreMs is the sum of occupied core-time, and uptimeMs is the amount of powered time. Every declared host contributes its idle energy while up, including hosts without application placements. This estimates CPU-related host energy only; network equipment, storage devices, batteries, charging losses and cooling are excluded.

The schema-2 observation horizon includes scheduled client timeout deadlines and all configured environmental transitions, even when a request has completed or an affected host is unused. Interrupted work and dropped packets have their obsolete completion events discarded; these cancelled events do not artificially prolong the horizon. Metrics.durationMs equals the final effective event time, and energy/uptime cover [0, durationMs]. Consequently, a request can finish at 27ms while a 1000ms timeout produces a 1000ms energy observation horizon. This deliberate difference from schema-1 trace-duration semantics is recorded in the schema.

Comparing energy requires interpreting the horizon as well as the completed work. A failed deployment may use less energy simply because it performed less work; energy alone is not a success criterion. All timings and power profiles are uncalibrated model inputs until measured against actual hardware.

## Schema 2 reference checks

The automated simulator tests include independently calculated cases:

| Case | Expected result |
| --- | --- |
| One 1000-byte request, 8000kbit/s, 5ms physical latency each way, 10+5ms processing | 27ms response latency |
| Same application moved to a 50ms-latency host | 117ms response latency |
| Two requests 1ms apart, zero processing, 1000 bytes on one shared 8kbit/s link | p95 3999ms, 4 transfers, 4000 delivered bytes |
| Two 10+10ms jobs on one shared host core, requests 1ms apart | p95 39ms; adding a second core reduces p95 to 20ms |
| Edge power outage [10,50), 60ms timeout, one retry in the first reference case | Completion at 87ms, one interrupted job, one durable write |
| Outage begins exactly at the original 21ms database completion | No write; the environmental transition wins |
| Outage begins exactly at 27ms response arrival after a 21ms write | Response lost; retry deduplicates the retained write |

Additional tests cover interrupted queues, dropped transmission backlogs, half-open/touching boundaries, unavailable client hosts, unused-host power, energy and transfer conservation, deterministic jitter, input immutability, cancellation and time bounds. A bounded fuzz target combines CPU capacity, retries, host outages and network outages while checking repeatability and conservation.

## Schema 3: exclusive workflows

A schema-3 application is a directed acyclic graph with one client, service and/or router processing nodes, and one or more terminal databases. All nodes must be reachable from the client and lead to a database. A client or service has exactly one outgoing edge; a router has at least two and selects exactly one for each logical request. Databases have no outgoing edges. Cycles, parallel fan-out, joins that synchronize multiple branches, and duplicate source/target edge pairs are rejected. Graph convergence is allowed: a shared downstream node receives whichever single branch was selected for that request.

A router first consumes its configured processing time and capacity, including a host CPU core when infrastructure exists. It then emits a `route_selected` trace identifying the router, logical request, attempt and selected application `edgeId`. Only the selected branch receives the request. A router is a weighted workload selector, not an interpreter for business rules or arbitrary predicates. There are no payload-dependent conditions in this version.

Routing is independent of simulation timing and network jitter. The exact selection algorithm is:

1. Sort outgoing edges lexicographically by their edge IDs. An omitted or zero `routeWeight` means 1; explicit weights range from 1 to 100.
2. Hash the UTF-8 string `decimalSeed + "\n" + requestID + "\n" + routerID` with SHA-256. Request IDs have the form `request-001`.
3. Interpret the first eight hash bytes as an unsigned big-endian integer. Take its remainder modulo the sum of the effective outgoing weights and select the corresponding cumulative-weight interval.

This gives reproducible weighted choices, without promising exact proportions for a small request count. Edge array ordering, graphical positions, placement changes, processing times, and jitter do not alter a request's routing choice. Changes to routing identities, the seed or weights may do so. Selection uses no samples from the jitter generator.

Each logical request keeps the same full route across all retries. A response retraces the selected edges in reverse, so a convergence point returns to the branch used by that attempt. Response forwarding consumes no additional CPU. Different requests may take different branches and compete for the same nodes, hosts and physical links. A router interrupted before finishing does not emit a selection event or forward work; a later retry still uses that logical request's fixed choice.

Deduplication state and duplicate-write accounting are scoped to the pair `(database node ID, logical request ID)`. Only databases can enable deduplication. A request attempts one terminal database, and retrying never chooses a different store. An unprotected store can commit duplicates while a protected store in another branch suppresses them. Committed state survives the previously described power-loss model. `dropFirstResponse` still loses the first successful store response per logical request after committing the write. Timed-out work is not cancelled; overlapping attempts and late responses retain the existing semantics.

## Schema 3: resources and portable profiles

With infrastructure present, every node has a placement and every application edge must have the required direct physical connectivity. The schema-2 CPU admission, memory reservation, bandwidth serialization, power/network interruption, durable writes and energy integration rules apply unchanged across branches and convergence points. A failure of one branch's host need not interrupt requests that use another branch, although shared links, hosts or nodes can still couple their performance.

Without infrastructure, each processing node has an independent FIFO resource limited by its `capacity`. Transfers use only application edge latency and seeded jitter. Memory is not admitted against fabricated hardware, no physical identities appear in the trace, and the run has no infrastructure metrics or energy estimate. Declared memory remains part of the component configuration and its profile validation, ready for a future placement.

Both schema-3 modes use the schema-2 observation horizon: scheduled client timeout deadlines and configured environmental transitions contribute to `durationMs`, while obsolete completions of cancelled work do not. An application-only request that completes before its deadline therefore still has a duration extending to that deadline. This differs intentionally from schema 1.

Reusable component packages declare bounded parameter profiles over the existing service, database and router kernels. Instantiation copies defaults into concrete node configuration. Simulation validates those values and the embedded package locks; it never silently replaces node values with package defaults. The full manifest, version, digest and node reference are included in portable project/run snapshots, so replay and validation need no catalog lookup or network download. The digest identifies the typed manifest content, not publisher trust. Packages add neither executable code nor new simulation primitives; arbitrary executable plugins, application generation and real deployment remain future work.
