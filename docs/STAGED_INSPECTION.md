# Staged design and the regional care inspection lab

The studio now separates three questions consistently:

- **Structure**: what boundary, parts, contracts and owners exist?
- **Behavior**: which rules, routes, scenarios or compatibility changes are possible?
- **Execution**: what happened in a particular experiment?

These are perspectives, not new abstraction levels. A data contract has validation evidence rather than an execution token. Pure components have invocation traces. State and message models have ordered events. Workflows have case tokens. Application/deployment models have timed request traces.

## Start here

1. Open **Inspection lab** in the main sidebar.
2. Select **Routine existing patient**. Read the expected result and coverage statement.
3. Click **Open design in workflows**. If you have an edited draft, the existing replacement protection applies. Recovery checkpoints remain available through the draft status control.
4. In **Structure**, read the root interface. The root shows stage boundaries instead of all atomic steps. The stage strip shows Arrival, Identification, Affiliation, Encounter, Intake, Financing and Dispatch, plus emergency and dependency recovery paths.
5. Click **01 Arrival**, then **Open Queue**. Only queue steps are drawn. The breadcrumb takes you back to Arrival or the full workflow.
6. Click a step to configure it in the right inspector. The left hierarchy lists steps in the focused stage. Required bindings, exact decision dependencies and owned commands retain their existing editors.
7. Expand **Boundary routes and interrupts**. Click an external destination to inspect that part of the design. Interrupts remain visible even when their target is outside the stage.
8. Open a decision dependency using the existing dependency inspector. Descend through exact component calls to primitive operations. This is executable component reuse; stage paths themselves are presentation grouping.
9. Select **Behavior → Scenario & expectations**. The scenario supplies synthetic task responses and independent expected outcomes, task counts and owner states.
10. Select **Execution → Interactive tasks** to respond to one task at a time, or run the scenario to save an immutable experiment.
11. In execution evidence, use **Previous**, **Next** and the recorded visit selector. **Follow token** expands the current stage. **Full map** shows the complete workflow. Loops retain separate visits.
12. Return to **Inspection lab** and run the routine check. Its embedded journey also supports replay. Then compare **Emergency after reservation** (select the exact similarly named exercise in the list): inspect ticket cancellation, reservation release and ECU acceptance.

The current visit is blue; previously visited stages are marked green. “Not visited” does not mean impossible or failed. A previously visited stage is not necessarily complete: a loop or interrupt can return to it. Outcomes are not marked successful before the corresponding evidence exists. Logical workflow steps have no inferred elapsed duration.

## Create your own stage hierarchy

1. Create or open a workflow.
2. Select a node and set **Stage path**, for example `Arrival/Queue` or `Intake/Clinical release`.
3. Assign other nodes to the same path to group them. Use `/` to add another level. Paths permit up to six levels and 240 bytes; empty segments are invalid.
4. Click the stage to focus it. Nodes added while focused inherit that path.
5. Use root or parent breadcrumbs to move up. Full-map routing remains available.
6. Validate, export, install and run as before. Stage metadata is part of the exact workflow definition and digest; change the version before replacing an installed identity.

Stage names can start with numbers to set a readable overview order (`01 Arrival`, `02 Identification`). This changes visual order only. `next`, branch conditions, command error routes and signals control execution. Stage boundaries list crossing routes; they do not introduce hidden edges or parallel execution.

**Stages are not executable child workflows.** They do not isolate variables, create child sessions, add contracts or support subworkflow calls. Existing recursive pure components and versioned state-machine dependencies remain reusable at arbitrary composition depths within engine bounds. A future executable workflow-composition feature needs separate scoped input/output and interruption semantics.

## Coverage map

The inspection pack is generated by `model.StudioInspectionPack()` and fetched from `GET /api/inspection`. It combines the current reference fixtures with a distinct staged reception workflow identity, `health.reception-inspection@1.0.0`. The original reception package and digests are unchanged.

| Area | Runnable exercise | What to inspect |
|---|---|---|
| Reception | Routine, registration, no affiliation, fever/release, incomplete evidence, unavailable resources, payment and emergency alternatives | Tasks, decisions, owners, signals, routes, loops, waiting outcomes and exact expectations |
| Reuse outside healthcare | Service desk workflow; education registry; school-library state/message scenarios | Same engine and reusable definitions with different domain values |
| Pure components | All reference component bundles with definition tests | Scalar primitives, exact nested calls, record/collection operations, access decisions and expected outputs |
| Data | Healthcare/education fixtures and deliberately broken affiliation reference | Records, keys, relationships, validation issues; broken reference must produce `valid=false` |
| State | Pharmacy and school-library reservations | Independent ownership, expected revisions, stale writes, replay, restart, durable/volatile state and effects |
| Messages | All reference delivery scenarios | Typed messages, dispatch/delivery distinction, frozen payloads, retry, rollback, lost acknowledgement and receipt replay |
| Timed application | Reliable pipeline and exclusive branching | Seeded routing, processing, timeout/retry, deduplication, requirements, metrics and request replay |
| Continuum | Edge/cloud placement, one-core burst, continuous edge power loss and local-link loss | Sites, hosts, placements, CPU/memory, links, bandwidth, power, outage intervals and energy estimates |
| UI/platform | Manual checklist in the lab | Authoring, library, inspectors, validation focus, JSON import/export, immutable catalog/history, autosave, conflict recovery and responsive/expanded canvases |

Each check displays the exact field and expected value used for its verdict. Workflow, state, message and component tests use independently authored expectations. Infrastructure exercises check the displayed metric; their other requirement verdicts are separate evidence, and can intentionally fail under outages. This is a feature inspection suite, not a claim of exhaustive combinatorial coverage of every primitive input or every failure interleaving.

## Run and inspect the complete suite

1. In the lab, choose **All engines**, then **Run visible checks**.
2. Experiments run sequentially. **Stop after current check** retains completed evidence and makes no claim about unrun cases.
3. Select each PASS or FAIL row. Compare its expected value, actual value and exact evidence.
4. Use **Open design** to edit the exact fixture in its native workspace. Run it there for that workspace's full graphical evidence and history.
5. Complete the separate manual checklist. Its checkmarks mean you inspected the behavior, not that an automated test verified it.
6. **Export inspection report** downloads the pack, results and checklist. **Export exercise** downloads one submitted request; native editors provide their own package/scenario/fixture export formats.
7. Reload: lab evidence and manual marks restore from IndexedDB. Server-backed runs also remain in each engine's PostgreSQL history. Component test reports are retained in the local lab report; individual saved evaluations are available through the Components workspace.

To run the same automated suite outside the UI:

```sh
STUDIO_URL=http://127.0.0.1:8080 node scripts/acceptance-inspection.mjs
```

Use a disposable database for acceptance testing. Tests intentionally create immutable experiment evidence. CI runs the new inspection suite alongside the existing API acceptance suites, frontend tests, Go race tests and Compose checks.

## Limits

For unified system executions, also follow [SYSTEM_REPLAY.md](SYSTEM_REPLAY.md).
The **Verify replay** action is in the System architecture Execution perspective,
separate from this lab's recorded workflow-visit playback. Inspect an exactly
reproduced failed scenario and confirm its independent expectations remain failed.
The API acceptance suite exercises pure, state and shared execution replays; the
automated inspection pack does not imply that it runs these unified-system checks.

The pack is a collection of independent experiments for one inspection story. The workflow engine does not drive the message engine or timed infrastructure engine. A simulated edge outage does not automatically interrupt an interactive workflow session. These integrations are not claimed.

No production clinical adapters, authentication/authorization enforcement, public marketplace, real deployment, multihop network routing, battery/solar model or automatic migration is introduced. Synthetic patient/actor IDs are test values. Exact access-policy comparisons are decisions, not an identity or authentication service.
